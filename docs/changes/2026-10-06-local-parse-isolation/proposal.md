## 问题与证据

顾问上传本地表格时，API 主线程执行 `parseData`，使其他请求等待。T10 的算法优化已让 100k×20 CSV 五轮解析中位达到 1.43 秒，但[健康接口探针](../2026-10-03-evidence-correctness-repair/evidence/api-profile-latency-20261006.json)测得 p95 从 6.73ms 升至 1180.52ms，增加 1173.79ms，超过 200ms 预算。探针使用真实 API 健康接口和同线程真实解析函数，未包含上传、数据库及对象存储，不代替完整链路验收。

## 建议范围

采用有界的本地解析 Worker Thread，将解析、画像、完整 normalized JSON 序列化移出 API 主线程；API 等待完成，保持现有本地上传同步成功响应及 Data Snapshot 发布语义。线程只执行平台固定代码，不调用模型、飞书、数据库或网络。

覆盖 CSV、Excel、JSON、粘贴输入及同一资产重新上传。保留 parserVersion、列映射、警告、类型和完整行；延续 50MiB、100万行、200列硬限制，以及 100k×20 的性能目标。每进程一个工作槽、不积压文件队列；繁忙、超时及资源失败有明确错误。

不扩展 Data Intake Job 的 provider，不改变本地成功合同为 202，不提供新的后台重试/取消接口，不修改飞书非幂等导入。未来需要刷新恢复或持久化排队时另行设计。

## 取舍与风险

线程隔离能解除解析对事件循环的直接占用，但不能提供操作系统级硬内存隔离；V8 heap 限制不包含 Buffer 和原生库内存。若边界实验无法证明受控失败，保持门禁失败并转为独立进程/服务方案，不宣称线程解决 OOM。一次一槽会让同进程同时上传返回繁忙，这是需要批准的新行为。JSON 的父线程反序列化和大消息复制同样可能阻塞，因此结果走临时文件，父线程仅接收受限元信息。

## 审核范围与验收

本次请求批准[设计](./design.md)和[任务](./task.md)所列的线程隔离、限流和错误合同；并不请求部署、生产数据操作或提交。验收见[测试计划](./test-plan.md)：数据语义相等、API p95 增量≤200ms、解析预算不退化、失败无半成品、线程/临时文件清理、API Console 同步及独立复核。
