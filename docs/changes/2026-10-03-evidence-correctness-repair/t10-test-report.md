## 根因审计与剩余缺口

历史第4轮授权读取 p95 增量 1018.871ms >200ms；同期健康增量约0.478ms。历史报告只有客户端耗时/状态，没有绝对时间戳、服务端阶段、数据库采样或在途数，不能补造这些信息。以下是待证伪假设，不是根因结论：

1. 数据库连接/查询排队：读取经过撤销 checkpoint、权限查询和资产/快照查询，共享 max5 连接；健康路径不依赖这些查询。需要请求阶段与连接等待相关性或可控复现，独立 monitor 查询快不能排除此假设。
2. 撤销账本文件 I/O 等待：就绪检查先读取账本再检查 checkpoint，不匹配才加锁恢复。需要记录账本读取/checkpoint/恢复各阶段耗时，不能因健康正常直接指认数据库。
3. 开放式客户端积压：每20ms发起请求而不等待前一个完成，新建连接；服务短暂变慢可能积压。新增在途数可以识别这种放大，但当前最大3且未复现，无法证明旧轮的因果顺序。

主线程整体解析阻塞与健康基本正常不相符，可能性较低；这不排除局部调度或短暂阻塞。两次新测量通过只证明本机这十轮满足预算，不解释历史红样本。**T10/G6 保持 VERIFYING，禁止以重跑成功关闭历史异常，也不推进依赖 T10 的 T11。** 下一步应在隔离环境补齐上述阶段测量并复现延迟；若无法复现，保留“历史根因未知”，不得将合理机制写为已证明原因。

同比/查找功能由本轮 data-engine 19/19 回归覆盖（闰日、周期分区、缺周期、零/负基数及高基数画像），源码/测试类型检查通过；API测试类型检查、三个修改脚本定向 ESLint/Prettier通过。本轮未重跑旧 G6 的 50MB/100万行/200列与展开输入资源探针，旧证据仍可追溯但不宣称本轮新验；完整 TP21 因历史异常未关闭。未改 API 合同或 Web，未运行全仓质量门禁。
