# 飞书表格接入恢复与工具审计：提案

- change-id：`CHG-2026-10-04-lark-intake-recovery`
- 状态：`DRAFT`
- 创建时间：2026-10-04
- 更新时间：2026-10-04

## 背景与问题

现有 CSV/Excel 飞书模式将上传文件导入为新云表，再由受限表格 Agent 选择工作表、表头和范围。`+workbook-import` 返回未就绪结果时，系统虽保存 `ticket`/`token`，仍把接入任务标为失败；Worker 过期后也只会失败，不会按已取得的引用续查。用户重新提交会创建另一份云表。接入审计只保存 Agent 决策和模型 token，不足以定位每条 CLI 命令的耗时、读取规模与失败阶段。

本提案是对现有上传导入链路的修复，不决定以后是否增加“读取已有飞书表格”入口，也不改变普通文件的默认接入路线。当前另有未完成的 `CHG-2026-10-03-evidence-correctness-repair`；本提案不覆盖其工作树修改或资源策略门禁。

## 目标用户与场景

咨询顾问上传 Excel 后，飞书服务端导入超过 CLI 本地等待窗口。系统保留该次导入的任务标识，安全续查至就绪，再读取表格并发布一个 Data Snapshot；页面能区分“正在等待云端导入”和“确定失败”。运维人员可从受控审计中判断命令类别、耗时与失败点，无需查看原始表格值或凭据。

## 本轮 MVP

- R1：已取得有效导入 `ticket` 时，只续查该 ticket；不再次调用 `+workbook-import`。
- R2：导入已就绪且取得 token 后，Worker 中断可继续读取同一云表；同一 intake job 最多发布一个 Snapshot。
- R3：外部调用可能已创建任务、但没有可验证 ticket/token 时，标为结果未知并停止自动重试；保留人工核查线索。
- R4：记录每条受限 CLI 调用的类别、耗时、结果、输出规模和错误码，记录真实模型 token；不记录原始单元格、凭据或完整 stderr。
- R5：保持现有 Project/Workspace/飞书身份绑定、来源快照及旧 Snapshot 不变规则；状态变化同步 API、API Console 和 Web。

## 明确不做

- 不新增读取已有飞书表格、实时同步、多用户 OAuth、自动删除云文件或大表分块读取。
- 不将模型决策当作数据完整性证明；选表语义验证另立需求。
- 不对已有失败任务自动批量恢复。旧任务仅允许明确的管理员核查和迁移判定。
- 不改变正在实施的图表渲染资源阈值或 Chart Revision 生命周期。

## 成功标准

1. 模拟 `ready=false` 且有 ticket 的导入，仅发生一次创建，之后通过同一 ticket 续查并成功发布一个 Snapshot。
2. 在导入返回、任务续查、表格读取、Snapshot 提交边界注入 Worker 中断，不出现自动重复导入或双 Snapshot。
3. ticket 缺失且结果不确定时停止并解释原因；旧 Snapshot 仍可用。
4. 审计能对齐每次 CLI 调用与 intake job，不含原始值或密钥；API 对普通用户只返回安全状态摘要。

## 待审核决策

- 是否先按本提案修复现有上传导入链路，或将当前优先级改为“连接已有飞书表格”。后者需要单独的产品方案。
- 云端副本的保留期限与人工清理责任尚未确定；本轮不会自动删除。
