# LangReport 市场研究

检索日期：2026-09-01

## 结论摘要

LangReport 的方向有实际价值，但“自然语言生成图表 + 可编辑 + 项目对话记忆 + 风格模板”已经不是稀缺功能组合。最直接的重叠对象是 Microsoft Research 的 Data Formulator：其当前公开仓库已经描述了数据线程、自然语言追问、可编辑图表、分支、持久化会话/工作区、主题与样式，以及报告分享；它还明确使用 Flint 作为图表基础。Julius、ChatGPT Projects、阿里云 Quick BI 智能小 Q 也分别覆盖了其中的大部分能力。

因此，LangReport 不应把产品定位成“又一个 AI 图表生成器”。更有机会的定位是：

> 面向产品、运营、咨询和研究团队的、可审核、可复现、带项目级业务口径和品牌规范的图表/报告工作台。

这条定位的核心资产不是模型本身，而是数据快照、变换计划、字段血缘、可解释的指标口径、不可变图表版本、审核流程和可控的模板系统。

## 主要产品风险与具体例子

### 1. 把“生成图表”误当作高价值问题

用户真正愿意持续付费的通常不是“画出一张柱状图”，而是“在截止时间前交付一份可信的、符合品牌的、可被复核的结果”。如果只是一次性生成图表，用户很容易直接使用 ChatGPT、Julius、Excel 或已有 BI 工具。

例子：运营人员问“做一张各渠道本月 ROI 图”。如果系统只给出图表，用户还要自行确认成本口径、退款是否扣除、时间区间、异常渠道、来源说明和导出格式；这时产品只节省了画图时间，没有解决交付责任。

### 2. “可编辑”必须定义清楚

至少有四种不同的编辑：

1. 外观：颜色、字体、标题、标签、布局；
2. 编码：图表类型、X/Y、颜色、分面、排序；
3. 数据变换：过滤、聚合、同比、占比、Join、派生字段；
4. 交付布局：多图排版、注释、脚注、报告页、PPT/Excel/网页嵌入。

例子：“改成按区域堆叠的百分比柱图，并只保留同比下降的区域”。这不只是换颜色或 mark，还会改变过滤、聚合、百分比计算、排序和图例。若编辑只改了视觉层，用户得到的仍可能是错误的业务结果。

### 3. 数据正确性比视觉效果更难

自然语言中的“收入”“订单数”“活跃用户”“同比”经常没有唯一含义。重复订单、退款、缺失月份、时区、含税/不含税和多表 Join 都可能让图表看起来合理但数字错误。

例子：订单表有一行商品明细，系统直接按行累加订单金额，会把一个订单的金额重复计算；或者同比计算使用了当前数据中存在的月份，而没有提示去年同期缺失。必须在结果旁展示过滤条件、聚合函数、公式、数据行数变化、警告、来源快照和可复核的中间结果。

### 4. 项目记忆可能变成污染源

“记住风格”容易实现，但“记住什么、在哪个作用域、何时失效”很难。项目 A 可能规定收入按不含税计算，项目 B 规定按含税计算；工作区级记忆若覆盖项目级规则，结果会被悄悄污染。

LangReport 当前设计的“候选—用户确认—项目/工作区记忆—冲突保留”是正确方向，但必须让用户看到本次生成实际使用了哪些记忆，以及为什么选择某个样式/口径。否则用户会把错误归因于模型，而不是发现记忆污染。

### 5. 风格模板不是调色板

Julius 已支持自定义 Chart Theme，Quick BI 已支持主题定制，Superset 也提供品牌 CSS。单纯增加更多颜色、字体和圆角不会形成壁垒。

真正可复用的“模板”应包含：适用数据字段、允许的图表类型、默认变换、指标格式、标题层级、脚注/来源、异常标注、移动端规则、PPT/网页尺寸、无障碍对比度、校验器和版本迁移策略。

如果“项目图标风格”指的是项目头像/图标，它更像装饰性配置，通常不是数据产品的购买理由；如果指的是图表的视觉风格，应改名为品牌化 Theme/Visual System，并与数据语义和交付规范绑定。

### 6. 聊天历史不是分析工作区

当用户连续生成十几张图时，单纯的消息列表会变成“图表坟场”。Quick BI 已增加画布来摆放图表、追问、查看血缘和合并成果；Data Formulator 用 Data Thread 和分支解决同类问题。

LangReport 需要让用户能从某一张图继续追问、复制分支、比较版本、把结果提升为 Chart Artifact，并看到“问题 → 变换 → 图表 → 报告”的关系，而不只是保存聊天记录。

### 7. 数据连接和团队治理决定 B2B 上限

当前仓库文档明确把数据库、外部 API、实时数据、跨文件 Join、Dashboard、实时协作和强监管合规放在 MVP 之外。这个边界适合做垂直 MVP，但意味着它暂时不能和 Power BI、Tableau、Quick BI、Superset 争夺完整 BI 平台预算。

例子：客户的销售数据每天从数仓刷新，财务、销售和代理商看到的字段和行权限不同。只支持上传 CSV 的产品无法保证自动刷新、权限隔离、历史版本、审计和嵌入，因此用户仍要把最终结果搬回 BI 或 Excel。

### 8. 安全和执行成本会快速上升

多轮 LLM、数据变换、校验、修复、渲染、导出和存储构成一条比普通聊天更贵的链路。用户还可能把恶意指令放进 CSV 单元格，诱导模型泄露数据或生成危险操作。LIDA 官方对生成并执行代码的安全提醒说明了这一类风险。

LangReport 采用受限 TransformPlan、独立 Worker、数据最小化和声明式插件是优势，但必须继续补齐沙箱、超时、资源限制、Prompt Injection 防护、租户隔离、数据保留/删除、BYOK、模型供应商策略和审计。

## LangReport 当前仓库的具体判断

### 已有的强点

- `Data Snapshot → TransformPlan → Flint Spec → Chart Revision` 的链路天然适合做可复现交付物。
- 不可变 Revision、字段血缘、主题快照、审核状态、评论和只读分享，比普通 AI 图表 Demo 更接近团队生产流程。
- 已设计 Project/Workspace 两层记忆，且要求候选确认、冲突显式保留，这比“自动记忆一切”更可信。
- Plugin Manifest 的固定版本、内容哈希、能力校验和 Revision 快照，为企业模板与校验器提供了正确的扩展边界。

### 当前容易被用户质疑的地方

- Web 页面使用 `local-dev-user` 和 `/api/v1/dev/bootstrap`，目前更像单项目演示，还没有完整的项目列表、项目创建和对话历史工作台。
- 当前合同中的生成图表类型仍主要是 Line/Bar/Area；用户可见编辑流程目前提交的是标题 patch，而不是完整的字段、聚合、过滤、编码和视觉编辑器。
- 合同虽然枚举了多个 Theme，但当前页面只展示部分预设；确定性 SVG renderer 对 `swiss` 做了特殊配色，其余主题仍复用同一基础色组，品牌风格尚未形成真实差异。
- API 已有 Conversation 表和创建/列表接口，但当前 Web 生成请求没有持有一个可见的 Conversation 状态，用户无法在界面上自然地切换、分支和回看项目对话。
- 文档已明确 MVP 不支持数据库、实时数据、跨文件 Join、Dashboard 和实时协作；这些不是缺陷本身，但必须在对外定位中诚实说明。

## 建议的切入方式

### 推荐定位

不要说：

> 和 AI 聊天，自动生成可编辑图表，还能记住项目风格。

建议说：

> 把 Excel/CSV 和业务问题变成可审核、可复现、符合品牌规范的图表与报告；每个结果都能回到数据快照、指标口径和变更版本。

### 推荐的第一垂直场景

优先选择有周期性、交付责任和重复风格的场景，例如：

- 咨询/代理团队：每周为多个客户生成品牌一致的经营分析图表；
- 运营团队：固定模板的周报/月报，能够替换新快照并保留差异；
- 用户研究团队：把问卷/访谈数据变成带脚注和口径说明的研究图表；
- 产品团队：围绕某个项目保存指标定义、实验口径和版本化图表。

这些场景会真正使用项目记忆、模板、版本和审核；“只想问一个数字”的用户则很容易被通用 AI 或既有 BI 满足。

### 优先级

1. 先做“审核级 Chart Artifact”：结果表、公式/变换、数据快照、字段血缘、警告、来源和 Revision diff 同屏可见。
2. 做混合编辑器：聊天负责意图和复杂变换，字段槽位/属性面板负责确定性编码和视觉修改；每次修改都能解释影响范围。
3. 把 Theme 做成“品牌设计系统 + 业务模板 + Validator”，而不是颜色选择器。
4. 为 Project Memory 增加可见来源、使用记录、过期策略、冲突处理和视觉偏好候选确认。
5. 选择性补充 PPT/Excel/网页嵌入、定时刷新和企业权限；不要在没有目标用户前先做通用 Dashboard 平台。

### 应该验证的指标

- 首次生成的指标/聚合正确率；
- 从上传到“审核通过”的时间；
- 用户需要重生成/手工修正的次数；
- 旧模板和旧项目记忆的复用率；
- 每个图表能否完整展示数据、变换和版本来源；
- 新数据快照到更新交付物的时间；
- 用户是否愿意分享/审核/再次使用，而不只是生成一次后离开。
